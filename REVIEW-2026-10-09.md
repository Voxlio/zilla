# Zilla — code review, 9 Oct 2026

Reviewed: `zilla2` @ Next.js 14.2.35 / React 18 / TypeScript / Tailwind v3 / shadcn-ui /
Dexie / lightweight-charts / Vitest. ~8,300 lines across `src/`.

Everything below was read in full. Six of the logic findings were **verified by running the
real implementation code** against textbook-correct inputs (see "Evidence" at the end) rather
than inferred by reading — those are marked **[proven]**.

---

## 1. What the project does, as built

A single-page browser app that produces one XAU/USD trade idea on demand.

- Three Next.js API routes (`/api/candles`, `/api/news`, `/api/calendar`) act as server-side
  proxies that hold the API keys and cache responses in a module-level `Map`.
- The browser fetches M15/H1/H4/D1 candles, then hands everything to a **web worker**
  (`src/workers/analysis.worker.ts`), which runs the whole analysis pipeline client-side:
  swing points → market structure (BOS/CHoCH) → fair value gaps → liquidity levels
  (swings + intermediate + session highs/lows) → premium/discount zones → a weighted list of
  "reasons" → a trade idea with entry, SL, TP1, TP2, R:R and a confidence score.
- Fundamentals are scored separately (`src/lib/fundamentals/scorer.ts`) from an economic
  calendar plus keyword matching on news headlines, and blended 70/30 with the technical score
  to choose the direction.
- `src/lib/explain/generator.ts` turns the trade idea into prose: a daily thesis, "Why This
  Trade", and an ELI8 "Simple Summary".
- Trades are written to IndexedDB via Dexie (`src/lib/history/`), surfaced on `/history`, and
  aggregated into a shareable PNG on `/scorecard`.

So the "no data leaves your browser" claim is **half true**: the analysis genuinely runs
locally in a worker, but candles/news/calendar are fetched through your own Next.js server,
which is where the third-party keys live. That's the right design — worth wording carefully on
the marketing side, because the server does see which symbol and timeframe you requested.

**The architecture is sound.** The worker boundary, the adapter interfaces, the
reason-objects-with-weights design, and the separation of analysis / explanation / history are
all good decisions. The problems below are almost entirely in the *implementations*, not the
structure, which is why most of them are cheap to fix.

## 2. CRITICAL

### C1 — Four live API keys are sitting in a file designed to be committed
`.env.example` contains real-looking keys for Twelve Data, Alpha Vantage, Finnhub and NewsAPI.
`.gitignore` only covers `.env*.local` (line 29), so `.env.example` would be tracked. `.env.local`
is byte-for-byte identical to it, which is how this happened — the example file was filled in
and used as the real config.

**Good news first:** `zilla2` is not a git repository yet — there's no `.git` directory — so
nothing has actually leaked. This is a landmine rather than a fire.

Why it still matters: `.env.example` is the one env file conventionally *meant* to be committed,
because it documents which variables exist. The first time you run `git init && git push`, all
four keys go public in the initial commit, and rewriting history afterwards doesn't un-publish
them. Free-tier keys are still your quota and your rate limit, and the Alpha Vantage one is
tied to your email.

Fix: replace the values in `.env.example` with placeholders now, keep the real ones only in
`.env.local` (already correctly ignored by line 29), and add `.env` to `.gitignore` for good
measure. Rotate the keys only if this folder has been shared, zipped, or synced somewhere
public — otherwise placeholders are enough.

### C2 — Fair value gap polarity is inverted **[proven]**
`src/lib/analysis/fvg.ts:23,35`

```ts
if (prev.low > next.high) { ... type: "bullish" }   // this is a gap DOWN
if (prev.high < next.low) { ... type: "bearish" }   // this is a gap UP
```

`prev.low > next.high` means the third candle's entire range sits *below* the first candle's
low — price fell and left a void. That is a **bearish** FVG. The two labels are swapped.

Verified output on valid OHLC data: a clean gap up is reported `bearish 101-105`; a clean gap
down is reported `bullish 105-109`.

Why it matters: this is the single most consequential bug in the app. `findEntry`
(`trade.ts:188,203`) looks for a *bullish* unmitigated FVG in the discount zone to place a buy
entry — so on every buy it is actually anchoring the entry to a bearish gap, and vice versa.
Every entry price the app has ever printed is derived from the wrong set of levels. The
"unmitigated bullish/bearish FVG" counts in the report and the FVG reason weights are all
mislabelled too.

### C3 — The fundamental score is sign-blind, so good and bad data push the same way **[proven]**
`src/lib/fundamentals/scorer.ts:93,96`

```ts
eventScore = -Math.abs(diff) * weight / 100;   // USD-positive events
eventScore =  Math.abs(diff) * weight / 100;   // USD-negative events
```

`Math.abs()` throws away whether the print *beat* or *missed* forecast. Verified: CPI 3.2 vs
3.0 (hot, bearish for gold) scores `-0`; CPI 2.8 vs 3.0 (cool, bullish for gold) also scores
`-0`. Same direction, both times.

Two more defects in the same function compound it:

- **Scale mismatch.** NFP 150K vs 180K scores **−27** (parseFloat drops the "K", so the surprise
  is "30"), while CPI 3.2 vs 3.0 scores **0** (0.2 × 0.9 = 0.18, which `Math.round` flattens to
  zero). Percentage-based releases — CPI, PPI, GDP, Retail Sales — contribute literally nothing,
  and one jobs number swamps everything else.
- **Missing forecast compares against zero** (`:64`, `parseFloat(event.forecast || "0")`).
  Verified: NFP 220K with no forecast scores **−100**, pegging the entire fundamental score to
  the rail off a single unforecast event.

Why it matters: this score is 30% of the direction decision in `trade.ts:48`. Right now that
30% is noise with a systematic bearish tilt. Note that `reasons.ts:365` gets the direction
*right* for the same event — so the app's own narrative can say "CPI miss, bullish for gold"
while the score it feeds into the decision says bearish.

### C4 — Silent fake price data
`src/app/api/candles/route.ts:56-58`

When Twelve Data and Alpha Vantage both fail, the route returns `generateMockCandles()` — a
random walk starting at `2000 + Math.random() * 100` — with **no flag in the response** saying
it's synthetic. The client can't tell, so the UI renders entry/SL/TP levels computed from
invented prices exactly as it renders real ones.

This is easy to trigger: Twelve Data's free tier is 8 requests/minute and the app makes 4
sequential candle requests per analysis (`api/trade.ts:176-190`), the route is
`force-dynamic`, and the cache is an in-process `Map` that empties on every cold start. A
rate-limit response returns `status: "error"` in a 200 body, which `fetchTwelveData` treats as
`null` → fallback → fallback → mock.

Fix direction: add a `source: "twelvedata" | "alphavantage" | "mock"` field to the response,
surface it in the UI, and refuse to show a trade idea built on `mock`.

### C5 — The price chart never renders
`src/app/page.tsx:34-90` with the chart container at `:431`

The chart-init effect has `[]` dependencies, so it runs exactly once after first mount. But the
`<div ref={chartRef}>` lives inside `{trade && (...)}` at `:346`, and `trade` is `null` on
first render — so the div isn't in the DOM, `chartRef.current` is `null`, the effect hits its
`if (!chartRef.current) return` guard and bails. When a trade arrives and the div mounts, the
effect never re-runs. `chartInstance.current` stays `null` forever.

Net effect: the chart area is permanently blank. The candle-update effect at `:93` also bails
immediately because `candleSeriesRef.current` is null, so `/api/candles` is being fetched on
every timeframe change for nothing.

### C6 — Outcome tracking is a no-op, so the Scorecard is permanently zero
`src/app/history/page.tsx:78`

```ts
await updateTradeOutcome(trade.id, []); // Pass empty array for now
```

Called with an empty candle array for every pending trade. Inside `updateTradeOutcome`
(`history/utils.ts:185`) the loop over candles does nothing, then `candles[candles.length - 1]`
is `candles[-1]` → `undefined` → `lastCandle.time` throws a `TypeError`, which the function's
own try/catch swallows into a `console.error`.

So every trade stays `"pending"` forever. `getHistoryStats` only counts `tp1|tp2|sl` as closed,
which means win rate, net R, avg R and best R are all structurally 0, and the equity curve on
`/scorecard` is always a flat line at zero. The entire results-tracking half of the product is
inert.

## 3. IMPORTANT

### I3.1 — Change of Character can never fire, and HH/LL are double-counted **[proven]**
`src/lib/analysis/structure.ts:98-217`

The bullish CHoCH check at `:145` requires `trend === "bearish"`, but the bullish BOS block
at `:107` has *identical* price conditions and already set `trend = "bullish"` 30 lines earlier
in the same iteration. The guard can never be true. Mirror image for bearish CHoCH.

Verified on a constructed downtrend-then-reversal: **3 BOS, 0 CHoCH**. `structure.choch` is
always an empty array. Downstream, the weight-95 "Change of Character" reason
(`reasons.ts:87-96`) — the highest-weighted signal in the whole system — can never appear, and
the CHoCH sentence in the report (`explain/generator.ts:142`) is dead code.

Separately, `higherHighs` and `lowerLows` get pushed twice for the same swing (once at `:122`,
again at `:189`). Verified: `higherHighs = [16,16,19,19]`. The "2HH, 1HL, 0LH, 2LL" line in the
M15 Breakdown is reporting double the real HH and LL counts.

### I3.2 — Session liquidity polarity is inverted, contradicting swing liquidity **[proven]**
`src/lib/analysis/liquidity.ts:181-201`

Session **high** is labelled `"sell-side"` and session **low** `"buy-side"` — the opposite of
`detectLiquidityFromSwings` (`:12-33`), which correctly maps swing high → buy-side and swing
low → sell-side. Verified: `2035 -> sell-side`, `2010 -> buy-side`.

Both conventions coexist in one combined array, so `findStopLoss` and `findTakeProfits`
(`trade.ts:239,288`) filter on `type` and silently get a mix of real levels and mirror-image
ones. `liquidity.test.ts` asserts the wrong behaviour explicitly ("Session low = buy-side
liquidity"), which is how it survived.

### I3.3 — Nearby levels of opposite type get merged into one **[proven]**
`src/lib/analysis/liquidity.ts:250-263`

The merge loop compares only `Math.abs(level.price - last.price) <= proximityThreshold` and
keeps `last.type`. Verified: a buy-side level at 2000.00 and a sell-side level at 2000.06
collapse into a single `buy-side` level at 2000.03. With a 0.10 threshold on gold this fires
often, and each time it silently deletes a level the trade logic needs.

Fix: only merge when `type` (and ideally `source`) match.

### I3.4 — No minimum R:R, so the app will confidently present a 1:0.01 trade
`src/lib/analysis/trade.ts:286-346`

TP1 snaps to the nearest liquidity level beyond entry with no distance check. If that level is
30 cents away while the stop is 50 dollars away, `riskReward` comes out around 0.006 and
`page.tsx:388` renders "1:0.01" in emerald green next to a 30%+ confidence score. The "Minimum
1:2 RR" comments only apply to the *fallback* branches where no liquidity was found.

Worse, `calculateConfidence` (`:157`) adds an R:R *boost* but never a penalty, and the floor at
`:163` is `Math.max(30, ...)` — so a structurally terrible setup still reports at least 30%
confidence.

Fix direction: enforce a configurable minimum R (skip liquidity targets closer than, say, 1.5R
and fall through to the R-multiple target), and let confidence fall below 30 when geometry is
bad.

### I3.5 — The "equilibrium" zone is mathematically unreachable
`zones.ts:40-48` sets `premium.bottom === discount.top === equilibrium`. Every downstream
three-way test therefore collapses to two outcomes:

- `zones.ts:62-68` — `getPriceZone` returns "equilibrium" only on an exact float match.
- `reasons.ts:300-324` — the `else` branch ("Equilibrium zone", neutral, weight 50) is dead.
- `explain/generator.ts:104-111` — a *third* copy of the same logic, same dead branch.

So price is always labelled premium or discount, however close to the midpoint it sits, and the
neutral phrasing variants at `explain/types.ts:164-167` never show. Fix: give equilibrium a real
band (e.g. 45–55% of range) and collapse the three duplicate implementations into one.

### I3.6 — Reason weights double-count and self-cancel, flattening confidence
`reasons.ts:169-189` pushes both "Buy-Side Liquidity" (bullish, 80) **and** "Sell-Side
Liquidity" (bearish, 80) whenever levels exist on both sides of price, which is nearly always.
They cancel in the score but still add 160 to `totalWeight`, which is the denominator of
`agreementRatio` in `calculateConfidence` (`trade.ts:154`). Same pattern at `:300-334`, where
"Price Location" (80) and "Distance from Equilibrium" (60) are the same signal counted twice
and always agree.

Result: confidence is systematically dragged toward the middle by filler reasons, and the
premium/discount signal carries 140 effective weight while structure carries 85.

### I3.7 — Division by zero reaches the screen as NaN / Infinity
- `reasons.ts:235` — `(currentPrice - low) / (high - low)` when a session has one candle →
  `NaN` → falls to the else branch → renders "Mid-range (NaN%)".
- `reasons.ts:327` — distance from equilibrium divides by `rangeHigh - rangeLow`, zero when
  `calculatePremiumDiscountZones` returns its all-zeros fallback (`zones.ts:14-20`, hit whenever
  the H4 *and* D1 feeds come back empty).
- `page.tsx:242` — `getRMultipleDisplay` divides by `risk` with no guard (currently harmless;
  the function is never called).

With the all-zeros zones fallback the app will happily render an entry of `$0.00` and a stop of
`$-0.50`. Needs a guard that refuses to build a trade idea from a degenerate range.

### I3.8 — Session position percentages are printed 100× too small
`reasons.ts:241,249` — `positionInRange` is a 0–1 ratio, and the near-high / near-low branches
call `.toFixed(0)` on it directly, producing "Near session high (1%)" and "Near session low
(0%)". The mid-range branch at `:257` multiplies by 100 correctly.

### I3.9 — Most of the plain-English phrasing library is unreachable
`explain/generator.ts:274` looks up `defaultPhrasingVariants[reason.label]` by exact label, but
`reasons.ts` emits labels that don't exist as keys: `"Calendar: CPI"` (key is `"Calendar"`),
`"LONDON Session Position"` (key is `"Session Position"`), plus `"FVG Count"`,
`"Untested Liquidity Pools"` and `"Distance from Equilibrium"`, which have no key at all.

Those all fall through to `` `${reason.label}: ${reason.value}` `` at `:287`, so the "Why This
Trade" tab shows raw debug-ish strings like `Distance from Equilibrium: +12.3%` instead of the
written sentences. Roughly 200 lines of carefully written copy in `explain/types.ts` is
effectively dead.

Note: fixing the lookup alone isn't enough — the Calendar and News Sentiment templates contain
`{event}`, `{diff}`, `{bullishScore}` and `{bearishScore}` placeholders that nothing ever
substitutes, so they'd render literally. Both halves need doing together.

### I3.10 — Chart price lines accumulate without ever being removed
`page.tsx:108-158` — the effect fires on every `[candles, trade]` change and calls
`addTradeLines`, which calls `createPriceLine` four more times. Change the timeframe five times
and the chart carries 20 stacked lines. Needs the returned `IPriceLine` handles kept in a ref
and removed before re-adding.

### I3.11 — Every analysis failure reports the same generic message
`analysis/worker.ts:22` *rejects* on an error response, so the `else` branch in `generateTrade`
(`api/trade.ts:142-146`) that reads `workerResponse.error` is unreachable. All failures land in
the outer `catch` and become "An unexpected error occurred while generating the trade idea" —
including the specific, actionable "Insufficient M15 candle data for analysis" thrown at
`analysis.worker.ts:75`.

There's also no timeout: if the worker never posts back, the promise never settles and the
Analyze button spins forever.

### I3.12 — News is dead in production
`fundamentals/scorer.ts:222-231,244-253` — both `FinnhubNewsAdapter.fetchNews()` and
`NewsApiAdapter.fetchNews()` are stubs that `return []` with a "would be implemented" comment.
`newsApiAdapter` (`api/trade.ts:77`) is constructed and never used. And `process.env.FINNHUB_API_KEY`
at `:74` is in a `"use client"` module, so Next.js replaces it with `undefined` in the browser
bundle regardless.

Meanwhile `/api/news/route.ts` is fully implemented, works, and **nothing ever calls it**. So in
production the headline half of the fundamental score is always exactly zero; in development
you get two hardcoded fake headlines. Fix is small: point the adapter at your own
`/api/news` route, same as the candles flow.

### I3.13 — Outcomes are recorded for trades that never filled
`history/utils.ts:137-181` walks candles from the start and checks TP/SL immediately, without
first checking whether price ever reached `entry`. Since entry is a *limit* level that can sit
well away from price, a trade that never triggered can be booked as a TP1 win or an SL loss.
Once C6 is fixed and real candles start flowing in, this will quietly corrupt the stats. Needs
a fill check first, then TP/SL evaluation only on candles after the fill.

### I3.14 — The UI tells you to type symbols it rejects
`page.tsx:646` says `Enter "XAUUSD", "Gold", or "XAU/USD"`, but `ASSET_CONFIGS` (`api/trade.ts:12`)
has the single key `XAUUSD` and `:99` does a bare `ASSET_CONFIGS[symbol.toUpperCase()]`. Typing
"Gold" or "XAU/USD" returns "Unsupported symbol". Needs an alias map.

### I3.15 — Scorecard headline stats ignore the selected range
`scorecard/page.tsx:64-73` — `getFilteredHistory` honours the 7d/30d/90d selector, but
`getHistoryStats()` always aggregates the entire table. So the equity curve changes when you
switch range and the win rate / net R above it don't, and the two contradict each other.

### I3.16 — Duplicate and stale-data fetches on both sub-pages
`history/page.tsx:101-108` has two effects that both call `fetchHistory`, and `fetchHistory` is
memoised on `[filters]` — so both fire on mount and both fire on every filter change.
`handleFilterChange` (`:87`) makes it worse: it calls `setFilters(newFilters)` then immediately
`await fetchHistory()`, which closes over the *old* `filters`. Three fetches per filter change,
one of them with stale criteria. Same double-effect pattern at `scorecard/page.tsx:166-173`.

### I3.17 — Candle requests are sequential
`api/trade.ts:176-190` — a `for` loop with `await` inside, so M15/H1/H4/D1 are fetched one
after another. Four round trips, each potentially hitting a cold upstream API. `Promise.all`
would make this ~4× faster and is a two-line change. (It also makes the rate-limit problem in
C4 more acute in bursts, so pair it with real caching.)

### I3.18 — The stylesheet is written for Tailwind v4 but the project runs v3
`globals.css` uses v4/shadcn-v4 idioms — `@import "tw-animate-css"`, `oklch()` values, a full
semantic token set as raw CSS variables — while `package.json` pins `tailwindcss: ^3.4.1` and
`globals.css` still uses the v3 `@tailwind base/components/utilities` directives.

In v3, utilities come from the config, and `tailwind.config.ts` extends **only** `background`
and `foreground`. So `bg-card`, `bg-card/50`, `text-muted-foreground`, `border-border/30`,
`bg-muted`, `text-destructive`, `bg-popover` and friends — used on essentially every element in
all three pages — generate no CSS at all. The hand-written `.border-border { }` and
`.outline-ring\/50 { }` rules at the bottom of `globals.css` are a workaround for an `@apply`
failure, which is the fingerprint of this mismatch.

Also: `.dark` is defined but nothing ever adds the class (`layout.tsx` has no `dark`, and
`tailwind.config.ts` has no `darkMode`), so the `:root` light values win — `--border` resolves
to near-white on a near-black page.

I could not run `next build` in this sandbox, so please eyeball the running app before
believing me on the severity. But the config/CSS mismatch itself is certain.

### I3.19 — The tests lock in the bugs rather than catching them
`__tests__/fvg.test.ts:44-56` constructs candles with `{ open: 100, high: 102, low: 105, close: 101 }` —
**low above high**, physically impossible — in order to make the inverted implementation pass.
The mitigation test at `:111` uses an FVG with `top: 100, bottom: 105`, also inverted. The file
still contains two abandoned candle arrays that are built and never used, plus the author's
working-it-out comments ("No, that's not right either", "I need to create proper FVG conditions").
`liquidity.test.ts:~150` asserts the inverted session mapping from I3.2 as expected behaviour.

So the suite is green while the logic is wrong, which is worse than having no suite — it
actively signals safety. These tests need rewriting from the financial definitions, not from
the current output. Expect a batch of them to go red when C2 and I3.2 are fixed; that's the fix
working.

### I3.20 — README is still create-next-app boilerplate
No description of what Zilla is, no list of required environment variables, no note that
analysis runs in a worker, nothing about `npm test`. For a solo project this is the
documentation you'll want in six months when you've forgotten why the 70/30 blend exists.

## 4. NICE-TO-HAVE

- `next.config.mjs:10` sets `eslint.ignoreDuringBuilds: true`, which is why the large number of
  unused imports (`history/page.tsx` imports 9 unused icons and components; `getAllHistory`,
  `candleApi`, `TradeIdea` unused there too) and unused parameters (`structure` in `findEntry`,
  `currentPrice` in `findStopLoss`, `assetConfig` in `buildTradeIdea`) go unnoticed.
- Dead exports never called from app code: `roundPrice`, `determineBias`, `calculateFibLevels`,
  `getTopReasons`, `getNearestFVG`, `getNearestLiquidity`, `markTestedLevels`, `getAllHistory`.
- `markTestedLevels` (`liquidity.ts:212`) is a no-op whose own comment admits it can't work, yet
  three functions `return markTestedLevels(levels)` as if it does. Harmless only because the
  worker separately calls `updateLiquidityTestedStatus`.
- `detectFVGs` already calls `mitigateFVGs` internally (`fvg.ts:48`), and
  `analysis.worker.ts:84` calls it a second time — the whole O(n·m) mitigation scan runs twice.
- `generateFullReport(trade)` is rebuilt inside three separate IIFEs in the JSX
  (`page.tsx:451,579,612`) with no `useMemo`, so it recomputes on every render.
- `trade.ts:354` uses deprecated `String.prototype.substr`; IDs are `Date.now()` + `Math.random()`
  rather than `crypto.randomUUID()`.
- `getAllHistory` (`history/utils.ts:65`) relies on `.reverse()` which orders by primary key —
  the string `id`. It approximates newest-first only because all current timestamps are 13
  digits. `orderBy("timestamp").reverse()` is what's meant.
- `getHistoryStats:218` seeds the `bestR` reduce with `0`, so best-R can never show a negative
  value even if every trade lost.
- `candlesChecked` (`history/utils.ts:158`) persists candle objects inside each trade row
  forever, unbounded.
- The same shapes are declared three times: `analysis/types.ts`, `explain/types.ts` and
  `fundamentals/types.ts` each define `CalendarEvent` / `NewsHeadline` / `AnalysisReport` /
  `WhatToWatch`. They agree today; they won't after the next edit.
- No position sizing anywhere, though the UI labels `|entry − SL|` as "Risk" — that's dollars
  per ounce, not account risk, and a beginner will read it as the latter.
- `scorecard/page.tsx:137` hardcodes `width: 1200, height: 800` for `toPng` regardless of the
  node's real size, and passes `quality`, which is a JPEG-only option.
- Mascot upload (`scorecard/page.tsx:119`) does no type or size validation before reading the
  file into a base64 data URL in state.
- `package.json` carries dependencies that aren't used or don't belong at runtime: `cn` (a
  different package from the local `cn` helper), `radix-ui` (the meta-package, alongside the
  individual `@radix-ui/*` ones), `shadcn` (a CLI, should be a devDependency at most),
  `@types/jest` (the project uses Vitest), `tw-animate-css` (a Tailwind v4 package).
- `vitest.config.ts` has the coverage block commented out, so there's no coverage signal.
- `api/candles.ts:27` passes `next: { revalidate: 300 }` to a browser-side `fetch`, where it's
  ignored.

## 6. Five upgrades worth doing after the fixes

1. **A golden-file backtest harness.** Freeze a few hundred real M15/H1/H4/D1 candles as a CSV
   fixture, run the full pipeline over it, and snapshot the resulting trade idea. Every future
   change to structure/FVG/liquidity then shows up as a readable diff instead of a silent
   behaviour change. Given how many of the bugs above were invisible, this is the highest-value
   thing you could add. *~1 day.*
2. **Make the data layer honest and cheap.** One `/api/analysis` route that fetches all four
   timeframes in parallel, caches to disk or Upstash/Redis rather than a per-process `Map`,
   returns an explicit `source` and `fetchedAt`, and fails closed instead of falling back to
